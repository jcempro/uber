API decidida (TypeScript puro browser, decimal.js consolidado; imports type de model):

- NUMERIC_RULES: objeto profundamente readonly e congelado; presets nonNegative=[0,+∞), positive=(0,+∞), fraction=[0,1]. Cada valor satisfaz NumericConstraints, maximum:null significa sem limite superior. Inclusividade explícita; sem mutação global Decimal.
- NumericValidationResult: união readonly {valid:true;value:DecimalText} | {valid:false;code:NumericValidationCode;message:string}. NumericValidationCode fechado: 'required'|'type'|'invalid-decimal'|'negative'|'out-of-range'|'invalid-constraints'. Mensagens específicas em pt-BR, não vazias. Não lançar exceção por entrada/configuração inválida.
- validateDecimalText(value:unknown,constraints:NumericConstraints):NumericValidationResult. Configuração é verificada primeiro, inclusive limites finitos/não negativos, tipos dos flags, min≤max e intervalo vazio (min=max com qualquer extremo exclusivo). Configuração inválida -> invalid-constraints. Não modificar entrada/configuração. null/undefined/string vazia ou somente whitespace -> required; demais não strings -> type. Não fazer coerção nem trim de valor válido.
- Formato de armazenamento JSON base10, não entrada localizada da UI: aceitar sinal, fração e expoente decimal (ex.: '+.5', '1.', '1e-400'). Regex lexical ^[+-]?(?:\d+(?:\.\d*)?|\.\d+)(?:[eE][+-]?\d+)?$ somente restringe sintaxe que Decimal ampliaria para hex/bin; parse/comparação via Decimal. Rejeitar whitespace periférico, vírgula, hex/bin, NaN, Infinity, expoente que gere não finito e malformed -> invalid-decimal. Decimal.lt(0) -> negative; -0 matemático aceito em nonNegative/fraction, rejeitado em positive. Limites inclusivos/exclusivos -> out-of-range. Sucesso preserva string exatamente. Nunca Number, parseFloat, toNumber, arredondamento ou aritmética própria.

Testes Vitest reais devem importar API e usar expectativas independentes deste contrato/RCF, nunca derivar valor esperado da implementação. Cobrir tabelas com:

1. Sucessos lexicais preservados: '0', '-0', '+.5', '1.', '0.295', '9007199254740993', '1e-400' em nonNegative; '1e-400' positive; '0'/'1' fraction. Presets integralmente congelados; execução não os altera.
2. required: undefined/null/''/'  '; type: 0/true/{}/[]; invalid-decimal: ' 1','1 ','1,2','0x10','0b1','NaN','Infinity','-Infinity','.','1e','1e9999999999999999'; negative: '-0.01'. Cada falha tem valid:false e code exato, mensagem pt-BR não vazia, sem value.
3. positive rejeita '0'/'-0'; fraction rejeita '1.0000000000000000000000000001'; aceita '0.9999999999999999999999999999'. Não usar Number para essas expectativas.
4. Intervalo independente [9007199254740993,9007199254740995]: aceita limites, rejeita 9007199254740992/9007199254740996. Com extremos exclusivos, rejeita limites e aceita 9007199254740994. Comparar também [0.295,0.295] inclusivo: aceita '0.295', rejeita '0.2949999999999999999999999999' e '0.2950000000000000000000000001'.
5. invalid-constraints: min>max, limite negativo/não finito/malformed, flags não boolean (fixture de runtime com cast unknown), min=max exclusivo, objeto null (runtime). Controles de domínio não devem aprovar coercion/zero silencioso. Não testar finanças ainda ausentes.
